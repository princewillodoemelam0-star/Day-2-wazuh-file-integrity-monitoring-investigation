Wazuh Security Investigation: Linux File Integrity Change

1. Incident Overview

During my security monitoring and investigation using Wazuh SIEM, I received an alert titled "Integrity checksum changed."

The alert indicated that a monitored Linux system had experienced a modification to a sensitive system configuration file.

Rather than immediately treating the activity as malicious, I approached the alert by examining the affected file, agent information, rule details, file metadata, and MITRE ATT&CK classification to understand what had happened and determine the appropriate response.

2. What Triggered the Alert?

The alert was generated by Wazuh File Integrity Monitoring (FIM), also known as Syscheck.

FIM monitors important files and directories for changes in their integrity and metadata.

In this investigation, Wazuh detected a modification to:

"/boot/efi/EFI/ubuntu/grub.cfg"

This file belongs to the GRUB bootloader configuration on a Linux Ubuntu system.

GRUB is responsible for presenting and loading the operating system during the boot process. Because this file is involved in system startup, unauthorized changes could potentially affect how the machine boots.

The alert was generated because Wazuh detected a change in the file's integrity information.

3. Step-by-Step Investigation

Step 1: Identify the affected endpoint

I started by identifying the system that generated the alert.

- Agent Name: ip-172-31-46-166
- Agent ID: 002
- Agent IP: 172.31.46.166
- Manager: ip-10-60-2-97

This helped me identify the monitored endpoint responsible for reporting the file integrity event.

The IP address belongs to the private 172.16.0.0/12 network range, which means it is an internal address rather than a publicly routable attacker IP.

Step 2: Examine the Wazuh rule

I reviewed the alert classification.

- Rule ID: 550
- Rule Level: 7
- Description: Integrity checksum changed.
- Decoder: syscheck_integrity_changed

The alert was generated by Wazuh's Syscheck component.

A level 7 alert indicates a security event that deserves investigation. However, the severity level alone does not establish that an attack occurred.

My next objective was to understand exactly which file had changed and what attributes were affected.

Step 3: Identify the modified file

After examining the full event log, I identified the affected file:

"/boot/efi/EFI/ubuntu/grub.cfg"

The log reported:

- File: grub.cfg
- Event: Modified
- Monitoring mode: Scheduled
- Changed attribute: inode
- Previous inode: 848
- New inode: 858

The inode is a filesystem identifier associated with a file.

The change from inode 848 to 858 indicates that the filesystem is reporting a different inode for the monitored path.

This can happen when a file is replaced or recreated rather than modified in place.

It is an important finding because it gives me a reason to investigate whether the file was legitimately regenerated or unexpectedly replaced.

Step 4: Examine file metadata

I reviewed the additional metadata available in the alert.

The event included:

- File owner: root
- Group owner: root
- User ID: 0
- Group ID: 0
- File size after change: 112 bytes
- Modification time after change: 2026-06-10 10:12:30
- Monitoring mode: scheduled
- Changed attribute: inode

The event also provided the following post-change integrity information:

- SHA1: 30e24f5518188c5092435b30ac859f4661a00077
- MD5: c8d6bfe53b3eca3bfb07e3ba59891038
- SHA256: aa2595ad0b0d9fbd018abea1fb168e2af07cab95466209b40084568444c26b0a

These hashes provide reference values for the file after the detected change.

I would compare them against a trusted baseline or previously recorded hash to determine whether the file's content also changed.

Investigation limitation: The screenshots provide the after-change hash values, but not the corresponding previous hashes or the actual contents of the file. Therefore, I cannot independently confirm the exact content modification from this alert alone.

Step 5: Understand why the file matters

The affected file is part of the Ubuntu GRUB bootloader configuration.

An unauthorized modification to a bootloader configuration file could potentially be used to:

- Alter boot parameters.
- Change kernel startup options.
- Redirect the boot process.
- Interfere with normal system startup.
- Support persistence or other malicious activity, depending on the changes made.

However, a GRUB configuration file can also change during legitimate operating system updates, kernel updates, bootloader maintenance, or administrative activity.

I would therefore investigate the activity that occurred around the time of the modification before determining whether it was malicious.

Step 6: Map the alert to MITRE ATT&CK

The Wazuh investigation interface mapped this alert to:

- Technique ID: T1565.001
- Technique: Stored Data Manipulation
- Tactic: Impact

This technique describes the manipulation of stored information to affect its integrity.

In this case, the mapping provides a useful security context because the alert involves an integrity change to a sensitive configuration file.

However, the MITRE mapping is a classification of the potential technique. It does not independently prove that an attacker manipulated the file.

I would validate the mapping against the actual file contents and surrounding activity.

Step 7: Determine whether the change was legitimate

At this stage, I would investigate the following:

1. Check whether an Ubuntu update or kernel upgrade occurred around the time of the event.
2. Review package management logs for activities involving GRUB.
3. Examine authentication logs to identify administrative access.
4. Check whether a privileged user executed commands that modified the configuration.
5. Compare the current file against a trusted backup or known-good configuration.
6. Review previous Wazuh FIM events for the same file.
7. Check for other unexpected changes to bootloader and system startup files.

Useful Linux investigation commands:

# View the affected file
sudo cat /boot/efi/EFI/ubuntu/grub.cfg

# Examine file metadata
sudo stat /boot/efi/EFI/ubuntu/grub.cfg

# Calculate the current SHA256 hash
sudo sha256sum /boot/efi/EFI/ubuntu/grub.cfg

# Check recent GRUB-related package activity
grep -i grub /var/log/dpkg.log

# Examine recent authentication activity
sudo journalctl -u ssh --since "2026-11-17"

# Review recent system activity
sudo journalctl --since "2026-11-17 17:00:00"

These commands are intended for authorized investigation on the affected Linux endpoint.

4. Security Risk Assessment

I classified this event as requiring further investigation because the affected file is associated with the operating system's boot process.

Potential risks include:

- Unauthorized boot configuration changes.
- Manipulation of system startup behavior.
- Potential persistence through boot configuration changes.
- Reduced system integrity and reliability.

However, I did not classify this event as a confirmed compromise because the available alert data does not establish malicious intent.

The scheduled detection mode and the inode change are findings that require correlation with system activity.

---

5. Incident Response and Remediation

If the investigation confirms that the change was unauthorized, I would recommend the following actions:

1. Preserve evidence

Save the Wazuh alert, file metadata, current hashes, relevant system logs, and a copy of the affected configuration for forensic analysis.

2. Validate the file

Compare the current GRUB configuration with a trusted backup or regenerate it using the approved operating system maintenance procedure.

3. Investigate privileged access

Identify who accessed the system and whether any unauthorized root-level commands were executed.

4. Contain the endpoint if compromise is suspected

Follow the organization's incident response procedure to isolate the affected host where necessary, while preserving forensic evidence.

5. Restore system integrity

If malicious modification is confirmed, restore the configuration from a trusted source and verify the bootloader and operating system.

6. Strengthen monitoring

Ensure that Wazuh continues monitoring sensitive bootloader files and other critical system configuration paths.

7. Monitor for recurrence

Watch for repeated integrity changes, suspicious privileged activity, unexpected file replacements, and other indicators of compromise.

---

6. How This Could Be Prevented

To reduce the risk of unauthorized system configuration changes:

- Restrict root access to authorized administrators.
- Apply least-privilege access controls.
- Monitor privileged commands and authentication activity.
- Maintain trusted backups of important system configurations.
- Keep the operating system and bootloader properly updated.
- Configure Wazuh FIM to monitor critical system files.
- Investigate unexpected changes promptly.
- Correlate file integrity events with package installation and system administration logs.

---

7. Final Investigation Conclusion

During this investigation, I analyzed a Wazuh Rule 550, Level 7 alert reporting an integrity change to the Ubuntu GRUB bootloader configuration file.

The alert originated from agent "ip-172-31-46-166", with agent ID "002" and internal IP address "172.31.46.166".

My investigation identified that the affected file was:

"/boot/efi/EFI/ubuntu/grub.cfg"

Wazuh reported that the file had been modified during a scheduled integrity scan, with its inode changing from 848 to 858.

The alert was associated with MITRE ATT&CK T1565.001 (Stored Data Manipulation), under the Impact tactic.

The event deserves attention because unauthorized changes to bootloader configuration files can affect system integrity and startup behavior.

However, based on the available evidence, I cannot conclude that this was a confirmed cyberattack. A legitimate system update or administrative action could also explain the change.

Final Status: Requires Further Investigation — Potentially Authorized or Unauthorized File Modification.

The next step is to correlate the event with system update records, privileged access logs, file contents, and a trusted integrity baseline before closing the investigation.
